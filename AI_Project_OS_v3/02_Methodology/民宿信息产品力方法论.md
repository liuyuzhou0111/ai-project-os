# 民宿信息产品力方法论

> 本文沉淀截至 2026 年 8 月上旬逐步形成的信息产品力工作方法。重点回答：一个信息项目应该怎么被定义、怎么被建设、怎么判断是否有效。

## 一、信息项目的起点：先定义用户决策

信息建设不是从字段开始，而是从用户问题开始。

需要优先回答：
- 用户在什么场景下会犹豫？
- 用户缺什么信息无法决策？
- 这个信息缺失会带来什么问题？
- 这个问题属于基础信任，还是特色价值表达？

**基本原则：先定义用户决策，再定义信息。**

## 二、从用户需求反推信息模型

确定用户需求后，需要继续拆解用户真正需要的是一个事实、一个结构关系、一个体验属性、一个标签，还是一个场景结论。

例如用户希望判断一个三居是否适合三个家庭入住，不能只收“卧室数=3”，还需要判断每间卧室是否独立、是否都有卫生间、公区是否足够、床型是否适配、是否存在共享干扰。

**信息模型应该能够支撑用户判断，而不是只完成字段覆盖。**

## 三、信息分层：事实 → 结构 → 体验 → 标签

### 第一层：事实信息
回答“有什么 / 是什么”。例如面积、卧室数量、卫生间数量、是否有泳池、是否有厨房。

### 第二层：结构信息
回答“这些东西之间是什么关系”。例如卧室和卫生间的对应关系、公区与卧室的关系、门店与房型的关系。

### 第三层：体验信息
回答“用户实际使用时是什么体验”。例如私享泳池、独立小院、270°观景、多家庭入住互不干扰。

### 第四层：用户标签
回答“为什么值得选 / 适合谁”。例如亲子友好、多家庭聚会、私汤度假、山景泳池、旅居友好。

**标签尽量不是原始采集项，而是下层信息组合后的表达结果。**

## 四、字段设计原则：最小有效信息集

字段设计优先考虑五个问题：
1. 用户是否真的会因为这个字段改变决策？
2. 房东是否能快速理解？
3. 房东是否能够准确填写？
4. 平台是否能够校验？
5. 用户端是否确定会使用？

如果答案不明确，优先不收。

**核心原则：少而关键 > 多而完整。**

## 五、信息生产方式：不要默认都让房东填

可能来源包括：
- 房东主动填写
- 平台已有数据推导
- 图片识别
- 文本 / LLM 抽取
- 房东自填 + 图片 + 算法 + 人工抽检的多源融合

**信息生产方式应该围绕成本、准确率和覆盖率综合设计，而不是默认增加表单。**

## 六、信息质量：覆盖不是终点

信息质量至少应看：覆盖率、准确率、完整度、一致性、可验证性、可使用性。

因此信息产品力不能只以覆盖率作为核心结果，应该逐步形成：

**覆盖 × 准确 × 使用 × 业务价值**

的评估体系。

## 七、信息治理：优先解决高价值错误

优先治理用户决策影响大的错误、高频负向反馈和高曝光商品。

例如卫生间数量错误、独卫标错、泳池属性错误、门店和房型关系错误。

**治理资源优先投向用户损失最大的地方。**

## 八、信息表达：采集语言与用户语言分离

商家端需要客观、简单、明确、可填写；用户端需要易理解、场景化、有吸引力。

例如商家填写“室外 + 私享 + 无边 + 山景”，用户端可包装成“私享山景无边泳池”。

**后台收事实，前台讲价值。**

## 九、信息层级：不同商品需要不同信息组织方式

信息不能永远只存在房源层，需要判断信息属于门店、房型、房源、空间还是库存。

客栈/酒店式公寓更适合门店 → 房型 → 库存；独栋别墅/独立小院更适合房源作为主要商品单元。

**先定义商品结构，再定义信息结构。**

## 十、信息项目推进方式：短期价值 + 长期能力

短期解决明确业务问题，长期沉淀可复用能力。

例如物业类型短期支持门店聚合，长期沉淀民宿分类体系；空间化短期提高多居信息表达，长期沉淀空间理解能力；图片项目长期沉淀视觉信息生产能力。

**每个项目都要回答：这次做完后，平台新增了什么长期能力。**

## 十一、效果验证：必须建立业务闭环

信息项目不能停留在“上线了”“覆盖了多少”。

需要判断用户是否看到了、是否使用了、决策是否改善、转化是否提升、NPS是否改善、负向反馈是否下降。

基础信息更关注NPS、负向反馈、取消、客诉；特色信息更关注点击、转化、间夜、用户偏好。

## 十二、完整工作链路

用户问题 → 定义决策场景 → 确定最小信息集 → 设计信息模型 → 确定信息生产方式 → 建立质量标准 → 商家端/算法建设 → 用户端表达 → 业务效果验证 → 治理与迭代 → 沉淀平台能力

## 核心原则总结

信息产品力不是“把更多信息填进系统”，而是：

**让平台更准确地理解商品，并把正确的信息在正确的场景表达给用户。**
